# Version 1.15 verification — 28 October 2026

Tests used the disposable Android 17/API 37 `Medium_Phone_API_37.0` emulator and fictional names, amounts and transactions. The connected personal phone was not used for database-clearing instrumentation. This document records executed checks and their limits.

## Build and automated checks

- `:app:testDebugUnitTest :app:assembleDebug :app:assembleDebugAndroidTest`: successful build; 119 JVM tests, zero failures and zero skips from the JUnit XML reports. The debug APK reports package `com.personalfinance.tracker`, `versionName=1.15`, `versionCode=3`, minimum API 26.
- The first complete Android run reached 64 tests and found one stale test assertion in `PersonalBackupManagerTest`: it compared a new transaction object with `createdOrder=0` to its correct persisted value `createdOrder=1`. The assertion now captures the saved record before restoring and verifies that restore does not replace it. The focused correction and two new synthetic release E2E cases passed together: 3 tests, zero failures. The fresh complete-suite result is recorded below.
- The release E2E cases exercise an income comment with emoji, quotes and newline through current CSV, family import and duplicate handling, personal restore, category rename/archive and historical identity, chart selection, persisted Home block settings and code fallback. Other Android tests separately exercise the system document picker and drag handle interactions. The original version 1.1 CSV decoder is preserved as a test fixture; the JVM compatibility test feeds it the explicit seven-column export.
- The biometric acceptance suite previously passed 10 focused Android tests, including six cases that drive the real Android prompt with an enrolled emulator finger. The user confirmed that the physical phone showed the automatic prompt after enabling biometrics, but a successful physical match and the full failure/recovery matrix were not independently confirmed. A real system-PIN recovery test currently fails on this emulator after the supplied PIN is entered: the test times out waiting for the application lock to disable. The no-PIN generic suite intentionally skips this opt-in case; this is an outstanding environment/behavior check, not a claimed pass.
